# CH07: 对话管理与上下文压缩

## 从一个真实问题说起

你和 AI 聊了 50 轮，对话越来越长。突然系统报错：

```
Error: Prompt too long (250k tokens). Maximum context window: 200k tokens.
```

**你的对话炸了！**

更糟糕的是，如果每次都把完整历史发给 AI：

- **第 1 轮**：1k tokens，花费 $0.003
- **第 10 轮**：10k tokens，花费 $0.03
- **第 50 轮**：50k tokens，花费 $0.15
- **总花费**：每轮越来越贵，累计成本暴增！

这就是为什么需要**对话管理与上下文压缩**：

1. **防止 Token 超限** → 对话可以无限延续
2. **控制成本** → Token 用量可控
3. **保留关键信息** → 压缩不丢失重要上下文

---

## 核心挑战：如何压缩而不丢失信息？

### 挑战 1：什么该保留？什么可以压缩？

```
对话历史：
[1] User: 帮我读取 config.yaml
[2] Assistant: [调用 Read 工具]
[3] Tool: [返回 5000 字的文件内容]
[4] User: 把 port 改成 8080
[5] Assistant: [调用 Write 工具]
[6] Tool: 写入成功
... (中间 40 轮)
[50] User: 刚才那个 port 改成多少了？
```

**如果压缩掉前面的历史，AI 就不知道 port 的值了！**

### 挑战 2：工具结果太大怎么办？

```
Tool: Read(large_file.json)
返回: 500KB 的 JSON 数据

问题：
- 这一条工具结果就占了 125k tokens！
- 但 AI 可能只需要其中一小部分
```

### 挑战 3：压缩后如何恢复状态？

```
压缩前：
- AI 刚读过 5 个文件的内容
- 正在执行某个 skill 的 SOP
- 知道可用的工具列表

压缩后：
- 历史变成一句摘要："用户在调试配置文件..."
- AI 忘记了刚读过什么文件
- 不知道当前在执行什么任务
```

**系统的解决方案：三层压缩架构**

```
Layer 0: 会话持久化（Session）
    → 对话保存到 .mewcode/sessions/xxx.jsonl
    → 支持恢复、列表、删除
  
Layer 1: 工具结果落盘（Tool Result Budget）
    → 单条超过 50KB → 落盘，只保留 2KB 预览
    → 聚合超过 200KB → 最大的几条落盘
    → 旧结果裁剪 → 保留近 10 轮，其余裁剪
  
Layer 2: 对话摘要压缩（Auto-Compact）
    → 前缀摘要 → 把前 N 轮压缩成一句话
    → 尾部保留 → 近期 10k tokens 原文保留
    → 状态恢复 → 附带最近读的文件和 skill
```

## Layer 0：会话持久化 - 让对话能恢复

### 核心数据结构

**SessionRecord**：持久化的最小单元

```python
# memory/session.py:32-43
class RecordType(str, Enum):
    SYSTEM_PROMPT = "system_prompt"
    USER = "user"
    ASSISTANT = "assistant"
    TOOL_RESULT = "tool_result"
    COMPRESSION = "compression"
    COMPACT_BOUNDARY = "compact_boundary"  # Layer 2 压缩标记

@dataclass
class SessionRecord:
    type: RecordType
    content: Any
    timestamp: datetime
    tool_use_id: str | None = None
    is_error: bool = False
```

**为什么需要 COMPACT_BOUNDARY？**

```
传统方式（只有 COMPRESSION）：
    压缩时：前缀压缩成摘要，写入 COMPRESSION record
    恢复时：读取所有 record，遇到 COMPRESSION 就插入摘要消息
    问题：前缀的原始 record 仍在文件中，恢复时要全部读取

新方式（COMPACT_BOUNDARY）：
    压缩时：写入 COMPACT_BOUNDARY，内联摘要 + 保留的尾部
    恢复时：只从最后一个 COMPACT_BOUNDARY 开始读取
    好处：前缀的原始 record 保留在磁盘（可审计），但不会被重放
```

### JSONL 格式持久化

**为什么选择 JSONL？**

```json
// session_20240924_142530_a7f3.jsonl
{"type":"user","content":"帮我读取 README.md","timestamp":"2024-09-24T14:25:30.123Z"}
{"type":"assistant","content":[{"type":"text","text":"好的"},{"type":"tool_use","id":"call_1","name":"Read","input":{"file_path":"README.md"}}],"timestamp":"2024-09-24T14:25:31.456Z"}
{"type":"tool_result","content":"# My Project\n...","timestamp":"2024-09-24T14:25:32.789Z","tool_use_id":"call_1","is_error":false}
```

**JSONL 的优势**：

1. **追加写入**：每轮只需 append，不用重写整个文件
2. **容错性强**：某一行损坏不影响其他行
3. **易于解析**：逐行读取，内存占用小
4. **人类可读**：调试时可以直接查看

### 消息链校验：防止 Tool Call 不完整

**问题：工具调用和结果必须配对**

```
正常的消息链：
[1] Assistant: [tool_use: call_1]
[2] Tool Result: [tool_use_id: call_1] → 配对完整 ✓

异常的消息链（中途崩溃）：
[1] Assistant: [tool_use: call_1]
[2] Assistant: [tool_use: call_2]  → call_1 没有结果！
[3] Tool Result: [tool_use_id: call_2]
```

**校验逻辑**：

```python
# memory/session.py:292-310
def validate_message_chain(records: list[SessionRecord]) -> int:
    """返回最后一个有效位置（所有工具调用都有结果）"""
    last_valid = 0
    pending_tool_uses: set[str] = set()
    
    for i, record in enumerate(records):
        # 发现工具调用，加入待匹配集合
        if record.type == RecordType.ASSISTANT and isinstance(record.content, list):
            for block in record.content:
                if isinstance(block, dict) and block.get("type") == "tool_use":
                    tool_id = block.get("id", "")
                    if tool_id:
                        pending_tool_uses.add(tool_id)
        
        # 收到工具结果，从待匹配集合移除
        if record.type == RecordType.TOOL_RESULT and record.tool_use_id:
            pending_tool_uses.discard(record.tool_use_id)
        
        # 所有工具调用都匹配完了，这是一个有效的边界
        if not pending_tool_uses:
            last_valid = i + 1
    
    return last_valid
```

**实际应用**：

```python
# memory/session.py:532-534

records = records[:valid_count]  # 截断到最后有效位置
messages = records_to_messages(records)
```

```python
# memory/session.py:500-548
def resume(self, session_id: str) -> ResumeResult | None:
    jsonl_path = self._sessions_dir / f"{session_id}.jsonl"
    meta_path = self._sessions_dir / f"{session_id}.meta"
    
    if not jsonl_path.exists():
        return None
    
    # 1. 加载元数据
    meta = SessionMeta.load(meta_path)
    if meta is None:
        return None
    
    # 2. 读取所有 record
    records: list[SessionRecord] = []
    with open(jsonl_path, encoding="utf-8") as f:
        for line in f:
            record = SessionRecord.from_jsonl(line)
            if record is not None:
                records.append(record)
    
    # 3. 重建压缩后的状态：仅从最后一个 compact_boundary 开始重放
    last_boundary = -1
    for i, rec in enumerate(records):
        if rec.type == RecordType.COMPACT_BOUNDARY:
            last_boundary = i
    if last_boundary >= 0:
        records = records[last_boundary:]  # 只保留 boundary 之后的
    
    # 4. 校验消息链完整性
    valid_count = validate_message_chain(records)
    records = records[:valid_count]
    
    # 5. 转换为 Message
    messages = records_to_messages(records)
    
    # 6. 重新打开文件用于追加
    file = open(jsonl_path, "a", encoding="utf-8")
    session = Session(session_id=session_id, file=file, meta=meta, sessions_dir=self._sessions_dir)
    
    return ResumeResult(session=session, messages=messages, last_active=meta.last_active)
```

**关键设计点**：

- **从 boundary 开始读取**：前缀已经被摘要，不需要重放
- **校验完整性**：截断不完整的工具调用
- **追加模式打开**：恢复后可以继续写入

## Layer 1：工具结果落盘 - 处理大型输出

### 三个问题

```
问题 1：单条结果太大
Tool: Read(large_log.txt)
返回: 500KB 日志文件
→ 单条就占 125k tokens！

问题 2：聚合结果太大
本轮对话：
- Read(file1.json): 30KB
- Read(file2.json): 40KB
- Read(file3.json): 50KB
- Grep(pattern): 100KB
→ 总共 220KB，超过 200KB 限制

问题 3：历史结果累积
50 轮对话，每轮都有工具输出
→ 总量越来越大，但旧的结果可能不再需要
```

### Pass 1：单条超限落盘

**阈值设计**：

```python
# context/manager.py:24-26
SINGLE_RESULT_CHAR_LIMIT = 50_000      # 单条超过 50KB → 落盘
PREVIEW_CHARS = 2_000                   # 只保留 2KB 预览
PERSISTED_TAG = "<persisted-output>"    # 标记已落盘
```

**落盘逻辑**：

```python
# context/manager.py:186-208
def persist_tool_result(tool_use_id: str, content: str, session_dir: Path) -> Path:
    """将工具结果写入文件"""
    file_path = session_dir / f"{tool_use_id}.txt"
    try:
        fd = os.open(str(file_path), os.O_WRONLY | os.O_CREAT | os.O_EXCL)
        with os.fdopen(fd, "w", encoding="utf-8") as f:
            f.write(content)
    except FileExistsError:
        pass  # 已经存在，跳过
    return file_path

def make_persisted_preview(content: str, file_path: Path) -> str:
    """生成预览消息"""
    size_kb = len(content.encode("utf-8")) // 1024
    preview = content[:PREVIEW_CHARS]
    return (
        f"{PERSISTED_TAG}\n"
        f"输出太大（{size_kb}KB），完整内容已保存到：\n"
        f"{file_path}\n"
        f"\n"
        f"预览（前 2KB）：\n"
        f"{preview}\n"
        f"</persisted-output>"
    )
```

**实际效果**：

```
原始输出（500KB）：

替换后（2KB）：
```

### Pass 2：聚合超限落盘

**问题：单条不超限，但总量超限**

```
本轮 5 条工具结果：
- call_1: 30KB
- call_2: 40KB
- call_3: 50KB  ← 这个最大
- call_4: 60KB  ← 这个更大
- call_5: 25KB

总计: 205KB > 200KB 聚合限制
```

**策略：优先落盘最大的**

```python
# context/manager.py:335-353
remaining = [tr for tr in fresh if tr.tool_use_id not in persisted_p1]
total = sum(len(c) for c in decisions.values()) + sum(len(tr.content) for tr in remaining)

        state.replacements[tr.tool_use_id] = preview

```

**实际效果**：

```
排序: [60KB, 50KB, 40KB, 30KB, 25KB]

第 1 步: 落盘 60KB → 剩余 145KB（还超限）
第 2 步: 落盘 50KB → 剩余 95KB（达标！）
第 3 步: 停止，保留其余 3 条
```

### Pass 3：陈旧结果裁剪

**问题：历史对话中的旧结果不再需要**

```
对话历史：
[轮 1] Read(config.yaml) → 5KB
[轮 2] Write(config.yaml) → "写入成功"
...
[轮 45] Read(data.json) → 50KB
[轮 46] 分析数据...
[轮 47] 继续分析...
[轮 50] 生成报告

当前在轮 50，轮 1 的配置文件内容还重要吗？
```

**策略：只保留近 10 轮的完整结果**

```python
# context/manager.py:28-30
KEEP_RECENT_TURNS = 10
OLD_RESULT_SNIP_CHARS = 2_000
SNIPPED_TAG = "<snipped>"
```

**裁剪逻辑**：

```python
# context/manager.py:231-276
def _snip_stale_messages(history: list[Message]) -> list[Message]:
    """裁剪陈旧的工具结果"""
    total_turns = _count_turns(history)  # 统计 assistant 回合数
    if total_turns <= KEEP_RECENT_TURNS:
        return history  # 对话不够长，不裁剪
    
    out: list[Message] = []
    turns_seen = 0
    old_boundary = total_turns - KEEP_RECENT_TURNS
    
    for msg in history:
        if msg.role == "assistant" and not msg.tool_uses:
            turns_seen += 1
        
        # 近期消息，或者没有工具结果 → 保留
        if turns_seen > old_boundary or not msg.tool_results:
            out.append(msg)
            continue
        
        # 旧的工具结果 → 裁剪
        new_results: list[ToolResultBlock] = []
        for tr in msg.tool_results:
            # 已经裁剪过或已经落盘 → 保留
            if (tr.content.startswith(SNIPPED_TAG) or 
                tr.content.startswith(PERSISTED_TAG) or 
                len(tr.content) <= OLD_RESULT_SNIP_CHARS):
                new_results.append(tr)
                continue
            
            # 裁剪为预览
            preview = tr.content[:200]
            new_content = (
                f"{SNIPPED_TAG}\n"
                f"(旧结果已裁剪，原始长度 {len(tr.content)} 字符)\n"
                f"{preview}\n"
                f"… (snipped)"
            )
            new_results.append(ToolResultBlock(
                tool_use_id=tr.tool_use_id,
                content=new_content,
                is_error=tr.is_error,
            ))
        
        out.append(_copy_message_with_results(msg, new_results))
    
    return out
```

## Layer 2：对话摘要压缩 - 核心算法

### 什么时候触发压缩？

**Token 用量估算**：

```python
# conversation.py:102-112
def current_tokens(self) -> int:
    """对当前对话中的 token 数量做出最佳估算"""
    # 有锚点时：baseline（真实用量）+ 锚点之后新增消息的字符估算
    if self.baseline_tokens <= 0:
        return estimate_tokens(self.history)  # 冷启动，全部估算
    
    tail = self.history[self.anchor_count:]
    return self.baseline_tokens + estimate_tokens(tail)
```

**什么是"锚点"？**

```
初始状态（无锚点）：
    baseline_tokens = 0
    anchor_count = 0
    → current_tokens() = 对整个 history 做字符估算

第 1 次 API 响应：
    input_tokens = 1200
    output_tokens = 300
    cache_read = 0
    → baseline_tokens = 1200 + 0 + 0 + 300 = 1500
    → anchor_count = 2（当前有 2 条消息）

新增消息后：
    history = [msg1, msg2, msg3]  # 新增 msg3
    → current_tokens() = 1500 + estimate_tokens([msg3])
```

**好处**：

- **精确估算**：前面的用量来自 API，不靠猜
- **增量计算**：只估算新增部分，快速
- **缓存友好**：和 API 的缓存机制对齐

**触发阈值**：

```python
# context/manager.py:32-34, 390-397
AUTO_COMPACT_SAFETY_MARGIN = 13_000
SUMMARY_OUTPUT_RESERVE = 20_000

def compute_compact_threshold(context_window: int, manual: bool = False) -> int:
    effective = context_window - SUMMARY_OUTPUT_RESERVE  # 预留摘要输出空间
    margin = MANUAL_COMPACT_SAFETY_MARGIN if manual else AUTO_COMPACT_SAFETY_MARGIN
    return effective - margin

def should_auto_compact(last_input_tokens: int, context_window: int) -> bool:
    return last_input_tokens >= compute_compact_threshold(context_window)
```

**实际计算**：

```
Claude Sonnet (200k context window):
    effective = 200k - 20k = 180k
    threshold = 180k - 13k = 167k
    
当 current_tokens() >= 167k 时触发自动压缩
```

**为什么要 13k margin？**

```
场景：current_tokens = 167k
1. 用户输入新消息: +500 tokens → 167.5k
2. 触发压缩，生成摘要请求: +167k（完整历史）+1k（摘要 prompt）= 168k
3. LLM 生成摘要: +5k tokens
4. 总用量: 167.5k + 5k = 172.5k < 180k ✓

如果没有 margin：
    threshold = 180k
    用户输入: 180.5k
    摘要请求: 181.5k → 💥 超限！
```

### 压缩的两部分：前缀摘要 + 尾部保留

**核心思想**：

```
完整历史（50 条消息）：
[1-40] 前缀（旧对话）→ 摘要压缩
[41-50] 尾部（近期对话）→ 原文保留

压缩后：
[摘要] "用户在调试配置文件，修改了 port 为 8080..."
[41] User: 现在测试一下
[42] Assistant: 好的
... 保留原文 ...
```

**为什么要保留尾部原文？**

- **上下文连贯性**：AI 能看到近期对话的原文，不依赖有损摘要
- **工具调用细节**：保留完整的参数和返回值
- **用户原话**：不丢失用户的精确表述

### 计算保留窗口

**目标：决定从哪条消息开始保留原文**

```python
# context/manager.py:38-42
KEEP_RECENT_TOKENS = 10_000      # 尾部累计不超过 10k tokens
MIN_KEEP_MESSAGES = 5            # 至少保留 5 条消息
KEEP_MAX_TOKENS = 40_000         # 最多累计 40k tokens（防止单条超大消息）
```

**算法**：

```python
# context/manager.py:634-672
def _compute_keep_start_index(messages: list[Message]) -> int:
    """决定压缩时尾部要原样保留多少条消息"""
    n = len(messages)
    if n == 0:
        return 0
    
    kept_tokens = 0
    kept_count = 0
    keep_start = n  # 尚未保留任何消息
    
    # 从尾部向头部遍历
    for i in range(n - 1, -1, -1):
        tok = _message_tokens(messages[i])
        
        # 已经保留了至少一条消息，且纳入当前消息会突破硬上限 → 停止
        if kept_count > 0 and kept_tokens + tok > KEEP_MAX_TOKENS:
            break
        
        kept_tokens += tok
        kept_count += 1
        keep_start = i
        
        # 保底条件已满足（token 下限或消息条数下限达到其一）→ 停止回溯
        if kept_tokens >= KEEP_RECENT_TOKENS or kept_count >= MIN_KEEP_MESSAGES:
            break
    
    return _align_keep_start_to_tool_pair(messages, keep_start)
```

**示例 1：正常情况**

```
消息列表（从新到旧）：
[50] 500 tokens
[49] 800 tokens  → 累计 1.3k
[48] 1200 tokens → 累计 2.5k
[47] 2000 tokens → 累计 4.5k
[46] 3000 tokens → 累计 7.5k
[45] 3000 tokens → 累计 10.5k → 达到 10k 阈值！

结果：keep_start = 45，保留 [45-50] 共 6 条消息
```

**示例 2：单条超大消息**

```

[49] 35000 tokens  → 单条就很大
[48] 1000 tokens
...

第 1 步：保留 [50]，累计 500 tokens
第 2 步：保留 [49]，累计 35500 tokens → 未达保底条件，继续
第 3 步：纳入 [48] 会达到 36500 tokens > 40k 硬上限 → 停止

结果：keep_start = 49，保留 [49-50] 共 2 条（不足 MIN_KEEP_MESSAGES=5，但被硬上限拦住）
```

**示例 3：消息数量保底**

```
[9] 500 tokens
[8] 500 tokens
```

**问题：不能拆散工具调用和结果**

```python
# context/manager.py:675-692
def _align_keep_start_to_tool_pair(messages: list[Message], keep_start: int) -> int:
    """把 keep_start 往前挪，确保不会保留孤立的 tool_result"""
    while 0 < keep_start < len(messages):
        msg = messages[keep_start]
        # 当前是 tool_result 消息
        if msg.role == "user" and msg.tool_results:
            prev = messages[keep_start - 1]
            # 前一条是对应的 tool_use 消息
            if prev.role == "assistant" and prev.tool_uses:
                keep_start -= 1  # 往前挪，把 tool_use 也纳入保留
                continue
        break
    return keep_start
```

```
    → 停止

最终 keep_start = 45，保留 [45-50]
```

### 熔断器：防止压缩死循环

**问题：压缩失败怎么办？**

```
场景：摘要生成失败（API 错误、token 超限等）

如果每次失败都重试：
    尝试 1: 失败
    尝试 2: 失败
    尝试 3: 失败
    ...
    → 无限循环，浪费 token！
```

**熔断器**：

```python
# context/manager.py:706-720
@dataclass
class CompactCircuitBreaker:
    max_failures: int = 3
    consecutive_failures: int = field(default=0, init=False)
    
    def record_failure(self) -> None:
        self.consecutive_failures += 1
    
    def record_success(self) -> None:
        self.consecutive_failures = 0
    
    def is_open(self) -> bool:
        """熔断器是否打开（拒绝压缩）"""
        return self.consecutive_failures >= self.max_failures
```

**使用**：

```python

    return "自动压缩已熔断（连续失败 3 次），请手动处理或使用 /compact"
```

**状态转换**：

```
初始: consecutive_failures = 0

第 1 次压缩失败: consecutive_failures = 1
第 2 次压缩失败: consecutive_failures = 2
第 3 次压缩失败: consecutive_failures = 3 → 熔断器打开

熔断后：
    自动压缩：拒绝
    手动压缩（/compact）：允许

某次压缩成功: consecutive_failures = 0 → 熔断器关闭
```

### 不值得压缩的情况

**问题：有时候压缩不划算**

```
场景 1：前缀太小

    压缩后节省：1500 - 500 = 1000 tokens
    → 摘要成本 3000 tokens > 节省 1000 tokens，亏本！

场景 2：全部消息都在保留窗口内
    对话只有 5 轮，全部被保留
    前缀为空
    → 没什么可压缩的
```

## COMPACT_BOUNDARY：压缩的持久化标记

### 为什么需要 COMPACT_BOUNDARY？

**传统 COMPRESSION 的问题**：

```
session.jsonl:
    [1] user: ...
    [2] assistant: ...
    [3] tool_result: ...
    ...
    [40] user: ...
    [41] compression: "摘要内容"  ← 压缩标记
    [42] user: ...
    [43] assistant: ...

恢复时：
    读取所有 record（1-43）
    遇到 compression 时插入摘要消息
    → 前 40 条 record 仍然被读取和解析（浪费）
```

**COMPACT_BOUNDARY 的设计**：

```
session.jsonl:
    [1] user: ...
    [2] assistant: ...
    ...
    [40] user: ...
    [41] compact_boundary: {
        "summary": "摘要内容",
        "keep": [  ← 内联保留的尾部消息
            {"type": "user", "content": "..."},
            {"type": "assistant", "content": ...},
            ...
        ]
    }
    [42] user: ...  ← 压缩后新追加的消息
    [43] assistant: ...

恢复时：
    找到最后一个 compact_boundary（record 41）
    只读取 record 41-43
    → 前 40 条 record 保留在磁盘（可审计），但不会被重放
```

### COMPACT_BOUNDARY 的结构

**构建**：

```python
# memory/session.py:152-167
def make_compact_boundary(summary: str, keep: list[Message]) -> SessionRecord:
    """构建一条 COMPACT_BOUNDARY record，内联摘要和原样保留的 keep 尾部"""
    keep_dicts: list[dict[str, Any]] = []
    for msg in keep:
        keep_dicts.extend(_message_to_record_dicts(msg))
    
    payload = {"summary": summary, "keep": keep_dicts}
    return SessionRecord(
        type=RecordType.COMPACT_BOUNDARY,
        content=payload,
        timestamp=datetime.now(timezone.utc),
    )
```

**解析**：

```python
# memory/session.py:170-197
def parse_compact_boundary(record: SessionRecord) -> tuple[str, list[Message]]:
    """返回 (summary, keep_messages)"""
    content = record.content
    if not isinstance(content, dict):
        return "", []  # 降级
    
    summary = content.get("summary", "")
    keep_raw = content.get("keep", [])
    
    # 重建 keep 消息
    keep_records: list[SessionRecord] = []
    for item in keep_raw:
        if not isinstance(item, dict) or "type" not in item:
            continue
        try:
            keep_records.append(SessionRecord(
                type=RecordType(item["type"]),
                content=item.get("content"),
                timestamp=record.timestamp,
                tool_use_id=item.get("tool_use_id"),
                is_error=item.get("is_error", False),
            ))
        except ValueError:
            continue
    
    return summary, records_to_messages(keep_records)
```

**使用**：

```python
# memory/session.py:242-250
if record.type == RecordType.COMPACT_BOUNDARY:
    # 内联展开：摘要作为 user 消息，后接原样保留的 keep 尾部
    summary, keep_messages = parse_compact_boundary(record)
    messages.append(
        Message(role="user", content="本次会话延续自之前的对话，因上下文空间不足进行了压缩。以下是早期对话的摘要：\n\n" + summary)
    )
    messages.extend(keep_messages)
    continue
```

## 代码亮点：设计模式与最佳实践

### 亮点 1：三层架构的职责分离

```
Layer 0 (Session):
    职责: 持久化
    不关心: 压缩算法
    
Layer 1 (Tool Result Budget):
    职责: 单条/聚合结果管理
    不关心: 对话摘要
    
Layer 2 (Auto-Compact):
    职责: 对话摘要
    不关心: 如何持久化
```

**好处**：

- **单一职责**：每层只做一件事
- **易于测试**：可以单独测试每一层
- **灵活组合**：可以只用 Layer 1 而不用 Layer 2

### 亮点 2：锚点机制 - 精确的 Token 估算

```python
# ❌ 坏做法：每次都估算整个历史
def current_tokens(self) -> int:
    return estimate_tokens(self.history)  # 全部重新估算

# ✅ 好做法：增量估算
def current_tokens(self) -> int:
    if self.baseline_tokens <= 0:
        return estimate_tokens(self.history)  # 冷启动
    tail = self.history[self.anchor_count:]
    return self.baseline_tokens + estimate_tokens(tail)  # 增量
```

**对比**：

```
50 轮对话：
    坏做法: estimate_tokens([msg1-msg50])  # 每次都算 50 条
    好做法: baseline + estimate_tokens([msg50])  # 只算 1 条
```

### 亮点 3：Design B - 不可变数据结构

```python
# ❌ 设计 A：原地修改
def apply_budget(conversation):
    for msg in conversation.history:
        if should_replace(msg):
            msg.content = new_content  # 修改原对象

# ✅ 设计 B：返回新对象
def apply_budget(conversation) -> ConversationManager:
    new_history = [process(msg) for msg in conversation.history]
    new_conv = ConversationManager()
    new_conv.history = new_history
    return new_conv  # 返回新对象
```

**好处**：

- **可追溯**：原对象保持不变，可以对比前后
- **易调试**：不用担心副作用
- **并发安全**：多个地方可以同时读取原对象

### 亮点 4：熔断器模式 - 防止死循环

```python
# 没有熔断器：
while True:
    try:
        compact()  # 可能一直失败
    except:
        continue  # 无限重试

# 有熔断器：
if breaker.is_open():
    return "已熔断"  # 拒绝压缩

try:
    compact()
    breaker.record_success()
except:
    breaker.record_failure()
    if breaker.is_open():
        notify_user("连续失败 3 次，已熔断")
```

### 亮点 5：Tool Pair 对齐 - 保证完整性

```python
# ❌ 坏做法：直接切分
keep_start = 46
keep = messages[keep_start:]  # [46-50]

# 问题：[46] 是 tool_result，但对应的 tool_use 在 [45]

# ✅ 好做法：对齐后再切分
keep_start = _align_keep_start_to_tool_pair(messages, 46)
# keep_start = 45（往前挪到 tool_use）
keep = messages[keep_start:]  # [45-50]
```

**保证**：

- **永远不会**出现孤立的 tool_result
- **永远保持** tool_use ↔ tool_result 配对完整

### 亮点 6：RecoveryState - 跨压缩的状态恢复

```python
# 压缩前：
recovery.record_file_read("config.yaml", "...")
recovery.record_skill_invocation("debug", "...")

# 压缩时：
attachment = build_recovery_attachment(recovery, tool_schemas)
# 附件包含：最近读的文件 + 激活的 skill + 可用工具

# 压缩后：
# AI 仍然能看到这些信息，无需重新读取文件或重新激活 skill
```

**好处**：

- **保留工作状态**：压缩不丢失关键上下文
- **减少重复操作**：不用重新读文件
- **提升用户体验**：对话更连贯

### 亮点 7：JSONL 格式 - 追加写入的智慧

```
为什么不用 JSON？
    {
      "messages": [
        {"role": "user", "content": "..."},
        {"role": "assistant", "content": "..."}
      ]
    }
    → 每次新消息都要重写整个文件

为什么用 JSONL？
    {"type":"user","content":"..."}
    {"type":"assistant","content":"..."}
    → 只需 append 一行

好处：
    ✓ 追加写入，快速
    ✓ 容错性强，一行损坏不影响其他行
    ✓ 易于流式读取
    ✓ 人类可读
```

## 总结

三层压缩架构解决了什么问题：

1. **Layer 0 (Session)**：持久化对话，支持恢复
2. **Layer 1 (Tool Result Budget)**：处理大型工具输出，防止 token 爆炸
3. **Layer 2 (Auto-Compact)**：摘要压缩对话，无限延续

**代码亮点**：

- ✨ **锚点机制**：精确的增量 token 估算
- ✨ **三层架构**：职责分离，易于维护
- ✨ **Design B**：不可变数据结构，易调试
- ✨ **熔断器**：防止压缩死循环
- ✨ **Tool Pair 对齐**：保证工具调用完整性
- ✨ **RecoveryState**：跨压缩的状态恢复
- ✨ **COMPACT_BOUNDARY**：高效的压缩标记
- ✨ **JSONL 格式**：追加写入，容错性强

核心原则：

- **增量优化**：只处理变化的部分
- **容错降级**：每一步都有 fallback
- **状态恢复**：压缩不丢失关键信息
- **成本控制**：智能压缩，减少 token 用量
